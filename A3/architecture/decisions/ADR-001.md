# ADR-001: Split the work into four builder agents, one independent reviewer and deterministic glue

- **Date:** 2026-11-21
- **Status:** Accepted
- **Decision area:** D1 (splitting the work)

## Context
The six stages differ in the knowledge and permissions they need. Requirements needs the issue but not the code (A1 skill rule R7: "do not design"). Design needs to read the code but not write it. Implementation needs write access. Testing should not inherit the implementer's assumptions. Release needs a write token but no intelligence. Review must be independent. One agent doing everything would carry the whole history (issue, design reasoning, failed attempts) in one context. Every later decision would then be biased by earlier ones, and the agent would grade its own work.

## Options considered
1. **One agent for everything** (mini-swe-agent style). Simplest to build, but it marks its own homework, the context grows with every retry, and it would need every permission at once.
2. **One agent per stage (6 agents).** Clean, but Release is a fixed sequence of `git`/`gh` commands. An LLM there only adds cost and a new way to fail (for example opening a PR against upstream).
3. **4 builder agents (Spec, Design, Implementer, Test) + 1 Reviewer, with code-only Gate/Release/Orchestrator.** ← chosen

## Decision
Use option 3. Each LLM role has its own prompt file (`prompts/*.md`), its own tool set (ADR-005) and receives only its hand-off (ADR-003). Implementer and Test agent are separate so that tests are written from the acceptance criteria, not from the implementer's reasoning. Stages that need no judgement (gate, release, all checks, all routing) are plain Python or shell. The five LLM roles share one brain adapter, so the model per role is configuration (ADR-006).

## Consequences
- + Each agent's context is small (spec about 2k tokens, design about 10–20k), so a cheap model is enough for builders.
- + A wrong call by one agent is caught by the next stage's code check, not by the same agent re-reading its own output.
- − More hand-off formats to keep stable (`spec.json`, `design.json`). Mitigated by schemas checked in `checks.py`.
- − Implementer and Test agent can disagree about the interface. The design's function list is their contract; a mismatch becomes a test failure and takes back-edge 4 → 3.
- Revisit if runs show the Test agent's tests mostly duplicate the implementer's understanding.
