# ADR-008: Reviewer independence through a separate job, a different model, a context limited to issue + diff + repo, and a prompt that must justify approval

- **Date:** 2026-11-21
- **Status:** Accepted (tested in experiment E1). Note: since ADR-011 the default reviewer is a different Gemini tier, not a different vendor.
- **Decision area:** D8 (reviewer independence)

## Context
A reviewer that sees the implementer's plan tends to check "did they do what they said" instead of "does this solve the user's problem safely". A reviewer from the same model family shares its blind spots. A reviewer that is asked "is this OK?" tends to say yes. GitHub also does not let `github-actions[bot]` approve or request changes on a PR it opened itself, so a formal review state cannot be used.

## Options considered
1. Same job and model as the builders, with a "now review" prompt. Cheapest, least independent.
2. A separate job with the same model and the full artifacts (spec, design, test report).
3. **A separate job, a different model family (ADR-006), only issue + diff + repo at PR head, read-and-run tools only, an adversarial checklist prompt, approval requires evidence.** ← chosen

## Decision
- **Separation:** `review` is its own job. It receives only the PR number and head SHA from earlier jobs and checks out the PR head itself.
- **Context:** the issue (untrusted), `gh pr diff`, and the repository. It may call `run_tests`. It cannot write files.
- **Prompt (`prompts/review.md`):** it is told the change was written by an automated agent that is often confidently wrong. It must (1) restate the user's request from the issue in its own words, (2) list at least 3 ways the diff could be wrong (edge cases, invariants in ARCHITECTURE.md §3, removed or weakened tests, scope creep, security), (3) check each with a tool call and record the evidence, and only then (4) give a verdict. A finding needs `file`, `line`, `problem`, `category` (code / tests / approach).
- **Anti-rubber-stamp rule in code:** an approval with no evidence entries, or from a reviewer that made no tool call, is downgraded to `request_changes` ("unsupported approval").
- **Posting:** a code step posts `review.md` as a PR comment with a verdict header and sets the label `autose:approved` or `autose:changes-requested`.
- **Calibration:** five seeded PRs (`experiment/seeded_prs/`: 1 correct, 4 with planted defects) measure catch rate and false alarms.

## Consequences
- + The reviewer judges against the user's words and the repo's invariants, not against our own spec.
- + Its quality is measurable on the seeded PRs.
- − Without the spec it may demand things the spec deliberately scoped out (false alarms). Experiment E1 measures this.
- − The review is a comment, not a formal GitHub review. Branch protection still requires a human approval to merge, which is the rule we want.
